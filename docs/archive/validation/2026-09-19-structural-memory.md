## 参考与取舍

重点阅读本机 EllesmereUI_GlobalSearch.lua：16–50 行为轻量文字和定位记录，385 行起为不创建真实控件的索引提取，搜索只服务设置导航。文件 SHA256 为 6FD33AF3DCB4BAB3A2D150E9F5E279E815B4D13820520BA4EA1C7E4F675C3918。上游位置：[EllesmereUI](https://github.com/EllesmereGaming/EllesmereUI)。采用轻量索引、结果阶段构造、固定行复用；不复制它的匹配规则，也不执行页面工厂来抓取数据。上游用途和 Lychee 全局业务搜索不同，不能直接比较主插件面板读数。

[SQLite FTS5](https://www.sqlite.org/fts5.html#external_content_and_contentless_tables) 将索引与外部内容分离，启发本次 SearchDocument / Entry 分离。[Elastic doc values](https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/doc-values) 区分按词查记录与按记录读字段，说明没有必要把所有业务字段都塞进倒排结构。WoW 无法照搬 mmap/磁盘页缓存，SavedVariables 加载后仍占 Lua 堆；本次不把 SV 当作内存卸载。

## 已实现

- 公共 RegisterProvider 支持 entryMode=documents 与 readEntry，默认 entries 不变；第三方和内置同样校验。Host Update 只保留 SearchDocument，不新增第二套 Catalog。
- reader 同步读取一个 ID；不执行业务、不扫描全库。命中读取失败标记不完整；更新、注销重入、错误 ID 与不匹配作用域均拒绝。明确恢复不依赖搜索可见性。
- 现有 CreateCatalog 修复被忽略的索引 checkpoint，暂停时间不占模糊评分预算；先取 K 个命中，缺失/重复再补查。一次性隔离记录移交调用方，省掉无意义的第二次完整深拷贝，不提供公开绕过校验能力。
- SDK 类型、协议、目录开发说明和性能规范同步，版本不变。

## 后续压缩实验：倒排成员布局

基于 623987c 的同一组离线目录，运行 `lua tests/performance_posting_storage.lua`。这是独立存储实验，不接入生产索引，也不代表完整查询优化已完成。

2025 条记录、3616 个编译字段，没有发现同字段规范化重复或标题/别名重复，故不增加无收益的字段去重逻辑。倒排表有 849 个字符键、501 个多成员表、19066 个成员。比较原哈希集合与每个编号三个字节的有序字符串；全部 101880 个成员判断逐项一致，随后各执行四轮（407520 次）。

| --- | ---: | ---: |
| 成员容器新增保留 | 849.81 KiB | 94.23 KiB |

两列都不包含共享记录、查询探针及 ID 映射的额外成本；有序串还没有处理增删、编号回收、取消和候选遍历顺序。该数字只能证明成员容器可以压缩，不能声称插件整体省了 89% 内存。时间是单次微基准，不是游戏延迟。

当前决定：不直接替换运行索引。压缩串的成员判断约慢 2.2 倍，且改变遍历顺序可能改变有预算的模糊候选。进一步实现必须同时证明：完整查询的召回/排序/高亮等价；更新、禁用、恢复及注销后编号和容器有界；初始化和增量写入分配可接受；全量实机保留与分配确有收益。优先比较低频只读目录的紧凑存储与高频可变索引分开处理，避免每次查询全量解压。

SDK / Provider API 保持 1.0.0 和具名字段。编号、压缩和缓存所有权属于内部实现，不要求第三方手工编码二进制，不新增持久化 schema，也不放松 reader 和外部修改隔离契约。
