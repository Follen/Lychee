2026-09-12；运行时代码基线 `ccd1c6a59dc3f431d33a90d7ece044b146545058`。未修改生产 Lua、SDK 协议或正式服安装。

## 结论

现有实现不适合每次关闭就清空、每次打开同步从头创建全部目录。离线完整重建是约 0.1～0.2 秒量级，热查询是零点几毫秒；细分后，SDK 校验为主要调查目标，索引次之。推荐先减少重复遍历及小表展开，再验证快速重开复用、闲置释放的生命周期。尚未证明任何候选方案同时满足整体休眠 <1 MiB 与体验等价。

下方完整目录重建表是 **离线数据，不是游戏测量，也不是 Alt+Space 首开延迟**。原生自动输入未成功打开聊天框；用户改为自行在 Lychee Dev 粘贴已校验的探针，第一份真实 API 采集证据已落盘，见下一节。上一轮真实客户端约 14.32 MiB 是另一个已创建面板的热开关采样，不能合并为本轮重建结果。本轮仅方案与有界调查；后续正式实现须先新建分支。

## 方法与范围

- Windows x64 Python 3.12 + Lupa Lua 5.1；`time.perf_counter` 高精度墙钟。WoW 和其他桌面程序仍在运行，存在调度噪声，不将最大样本剔除。
- 复用 `tests/performance_startup.lua` 的 30 文件 bootstrap 和真实 Provider → SDK → Registry → StaticIndex → Query 实现。没有真实 Frame 引擎、UI 创建、动画、原生 AddOn 加载和完整 79 文件 TOC。
- zhCN 首领 1154 条，菜单与纹章 35 条，模拟坐骑分别 287 / 1500 条，共 1476 / 2689 条。287 对应此前已收集数量，但名称及 getter 都来自测试夹具；真实 API 还可能遍历大量未收集坐骑。
- 每档 11 轮，第一轮单列，其余 10 轮统计。每轮确实重新读取模拟 API、构造业务记录、经 SDK 校验/复制和索引编译；关闭后注销四个 Provider，清理查询与规范化缓存。代码和工厂保留，并非重新加载 Lua。
- Registry 在测量前 ready；私有夹具没有 C_Timer，中文静态目录同步执行。完整构建时间就是此夹具的一段不可让出的同步耗时，不是多个批次相加。不能据此断言生产所有语言和 Provider 都同步。
- 计时路径无 debug hook。业务校验和序列化不计入构建/热查询时间。每轮验证完整记录及 12 个查询的顺序、字段、动作描述和载荷不变；不执行游戏动作，不能替代 UI/业务端到端验收。
- 旧记录/索引用弱引用检查回收；Registry、来源和查询任务清空断言通过。模拟 native 根一直保留，数量 2，不能作为真实控件内存证明。

## 候选方案取舍与推荐顺序

| 候选 | 当前判断 | 下一项决定性验证 |
| --- | --- | --- |
| 每次开关全量重建/销毁 | 当前直接采用会引入昂贵同步工作；不能声称几毫秒 | 优化后真实完整首查及最大同步跨度 |
| 永久保留全部现有缓存 | 现有热查询快，但无法解决闲置总量 | 无需作为最终方案重复验证 |
| 紧凑记录/索引 + 合并接收校验 | 首选有证据的实验，兼顾分配、保留和恢复成本 | 同数据结果/顺序/动作等价，非法数据与外部修改隔离仍通过 |
| 少量昂贵缓存 | 候选，须按实测每字节节约的重建时间决定 | 实际取得成本与缓存总字节，不先保留所有首领/成就 |
| 快速重开温缓存 + 分层过期 | 推荐生命周期方向，期限不是已定参数 | 连续开关不卡、过期无活动资源、休眠恢复不缺结果 |
| 原生 LoD 拆包 | 可研究首次使用前成本；不能降低使用后全部已加载代码成本 | 所有伴随包总量及完整使用后固定成本，不只看 Lychee 名下 |

SDK 3 可破坏式升级：轻声明与活动实例分离，活动上下文统一拥有查询、订阅、timer、结果和视图；过期使旧回调失效，恢复从权威来源重建。业务 ID、固定、历史、排序和动作保持。原生控件采用有上限复用，不假设 Hide 能销毁；代码/工厂仍保留的部分照常计入预算。

实施入口是 P0 可行性实验：先查剩余代码、工厂、必要控件及存档的固定下限，再做紧凑记录与一次接收实验，最后选恢复缓存策略。没有使用后固定成本证据，不推进以「已可达 1 MiB」为前提的完整重写。
